## §1 — Register task and set up the scene (robot, objects)

### Description

A manager-based task is registered with `gym.register(id=..., entry_point="isaaclab.envs:ManagerBasedRLEnv", kwargs={"env_cfg_entry_point": "<dotted.path>:<TaskName>EnvCfg"})` inside the per-robot `__init__.py`. The env class is generic — the *shape* of the task lives entirely in the `*EnvCfg` dataclass. The scene (ground plane, table, robot articulation, lights, cameras) is composed in a `@configclass class <Task>SceneCfg(InteractiveSceneCfg)` block; the env-cfg holds an instance of that scene plus the manager dataclasses. Robot articulations come from `isaaclab_assets` (e.g. `FRANKA_PANDA_CFG`) and are slotted in via `__post_init__` (`self.scene.robot = FRANKA_PANDA_CFG.replace(prim_path="{ENV_REGEX_NS}/Robot")`). Static props are loaded from Nucleus via `${ISAAC_NUCLEUS_DIR}/Props/...` URLs. The smoke that proves §1 wired correctly is `gym.make(<id>, cfg=parse_env_cfg(<id>))` returning observation_space + action_space without exception.

## §2 — Action types (delta / absolute joint position, delta / absolute end-effector pose)

### Description

Manager-based action specs live in a `@configclass class ActionsCfg` dataclass. Each field is an `ActionTermCfg` subclass; `ManagerBasedRLEnv` instantiates an `ActionTerm` per field at startup. The action vector concatenates fields in declaration order. Per-robot env-cfgs override `self.actions.<field>` in `__post_init__`. The canonical Reach task uses **`JointPositionActionCfg(scale=0.5, use_default_offset=True)`** — absolute joint position with default-offset = the URDF home pose, so policy outputs are *deltas around home* in joint space. For end-effector control, IsaacLab supplies `DifferentialInverseKinematicsActionCfg`; the same class handles **abs and delta** EE pose via `controller=DifferentialIKControllerCfg(use_relative_mode={False|True})` (see `config/franka/ik_abs_env_cfg.py` vs `config/franka/ik_rel_env_cfg.py`). For grippers, use `BinaryJointPositionActionCfg`.

## §3 — Initialize / reset the task

### Description

Manager-based reset is *event-driven*: there is no `_reset_idx` body. Instead, an `EventCfg` dataclass declares `EventTerm`s with `mode="reset"` — when `env.reset()` runs (whole-env reset on episode boundaries, single-env reset on success/timeout), the `EventManager` sweeps every `mode="reset"` term in declaration order. Common terms: `mdp.reset_joints_by_scale` (scales URDF home joint positions by a uniform factor), `mdp.reset_root_state_uniform` (samples root pose + velocity from a uniform distribution), `mdp.reset_scene_to_default` (mass-reset everything to USD defaults). Every term reads from a fixed param schema documented in `source/isaaclab/isaaclab/envs/mdp/events.py`. The same `EventCfg` class is also where DR (§7) lives — distinguish reset-time-only terms (`mode="reset"`) from startup terms (`mode="startup"`, fired once at scene-build) and interval terms (`mode="interval"`, fired every N seconds).

| Reset event functions library | `source/isaaclab/isaaclab/envs/mdp/events.py` (re-exported from `isaaclab.envs.mdp`) — most-used: `reset_joints_by_scale`, `reset_joints_by_offset`, `reset_root_state_uniform`, `reset_scene_to_default` |

### Decisions the future agent must resolve

- Initial joint distribution. `reset_joints_by_scale` (multiplicative, robot-home-anchored) is the Reach default. `reset_joints_by_offset` (additive, range in radians) is preferred when the task has a fixed start pose (e.g. arm pointing forward). Sample range is task-specific — ask user.
- Object / root-pose randomization. For tasks with movable objects (Lift / Push), add a `mdp.reset_root_state_uniform` term keyed on the object's `SceneEntityCfg`. Ranges depend on workspace bounds.
- Velocity reset. Default to `(0.0, 0.0)` unless the task explicitly trains under non-zero initial velocity (e.g. throwing / catching).

## §4 — Goal and termination

### Description

Goal sampling and termination are split across two managers. **Goals** live in `CommandsCfg` (`@configclass class CommandsCfg`) — a dict-of-CommandTermCfg dataclass. Each command term resamples on its own clock (`resampling_time_range`) and exposes the current command via `mdp.generated_commands` in observations. The Reach task uses `mdp.UniformPoseCommandCfg` to sample 6-DoF EE goals every 4 sim seconds (and writes the body's pose-xform-target into the policy obs as `pose_command`). Other common command types: `mdp.UniformVelocityCommandCfg` (locomotion velocity targets), `mdp.NullCommandCfg` (placeholder for tasks without an explicit goal channel — the goal is implicit, e.g. "lift cube above 0.04m"). **Termination** lives in `TerminationsCfg` — a dataclass of `TerminationTermCfg` (alias `DoneTerm`). Each term returns a `bool` tensor of shape `(num_envs,)`; the env ORs them together. `mdp.time_out` (with `time_out=True` flag — that flag *also* marks the term as a truncation, not a true termination, which RL training scripts use to bootstrap value targets). Failure terminations: `mdp.illegal_contact`, `mdp.root_height_below_minimum`, etc. Success terminations are typically *not* a TerminationTerm — success is recorded as an `info["is_success"]` term inside `ObservationsCfg` (or a `RewardsCfg` term with weight 0 just for logging) so the episode runs the full horizon and the agent gets the dense success signal — see Lift's `object_reached_goal` term for the canonical pattern.

## §5 — Observation

### Description

Observations are produced by the `ObservationManager` from a `@configclass class ObservationsCfg` dataclass. Each top-level field is an `@configclass class <Name>Cfg(ObsGroup)` group; the `policy` group is mandatory (training algorithms read from it), `critic` is conventional for asymmetric actor-critic, additional groups are user-defined. Inside a group, each field is an `ObsTerm(func=<callable>, params=..., noise=...)`. Functions live in `isaaclab.envs.mdp.observations` and are re-exported under `isaaclab.envs.mdp` — common ones: `joint_pos_rel` (joint pos minus URDF default), `joint_vel_rel`, `last_action`, `generated_commands` (current value of a command term), `base_lin_vel` / `base_ang_vel` (root velocity in body frame), `body_position_in_robot_root_frame` / `body_quat_in_robot_root_frame` (object pose in robot base frame). The `enable_corruption=True` flag in `__post_init__` activates the per-term `noise=...` argument; `concatenate_terms=True` flattens the group into a single `Box(-inf, inf, (sum_of_term_dims,), float32)`. Without `concatenate_terms=True` the group becomes a `Dict` of named per-term tensors. Reach concatenates 4 terms into a 32-dim vector (=7 joint_pos + 7 joint_vel + 7 pose_command + 7 last_action — with command rounding the actual count is 32 = 9+9+7+7 because pose_command emits xyz+quat = 7 dims and joint_pos/vel/last_action are each 9-dim including the gripper joints in the regex; check `obs_dim` from §1's smoke for the exact number on a new task).

### File pointers

| Obs term | Source |
|----------|--------|
| Proprio (joint pos / vel) | `mdp.joint_pos_rel`, `mdp.joint_vel_rel` (Reach uses both); `source/isaaclab/isaaclab/envs/mdp/observations.py` |
| Last action | `mdp.last_action` |
| Goal / command channel | `mdp.generated_commands` keyed by `params={"command_name": "<command_field>"}` (Reach uses `"ee_pose"`) |
| Object state | `mdp.root_pos_w`, `mdp.root_lin_vel_b`, `mdp.body_position_in_robot_root_frame` (object-pose-in-robot-base-frame helpers); see `source/isaaclab_tasks/.../manipulation/lift/mdp/observations.py` for object-specific examples |
| Sensor / image | Camera observations live under `mdp.camera_observations`; tile-render via `tiled_camera`. Reach has no cameras. |
| Reference: ObservationsCfg | `source/isaaclab_tasks/isaaclab_tasks/manager_based/manipulation/reach/reach_env_cfg.py:ObservationsCfg.PolicyCfg` (lines 102–117) |

### Decisions the future agent must resolve

- Term selection. Reach's 4 terms are the minimal "proprio + goal + last action" set. Add `mdp.body_pos_w` / `mdp.body_lin_vel_w` for tasks where the EE / object pose itself matters; add object-state terms for manipulation; add `mdp.base_lin_vel` / `mdp.projected_gravity` for locomotion. Ask user.

- Asymmetric critic. Add a `critic` group with privileged ground-truth terms only if the user is training with PPO + AC critic (rsl_rl). Skip for SAC/TD3 — they typically don't use it.

## §6 — Reward (read by `reward-generator`)

### Description

Reward is computed by the `RewardManager` from a `@configclass class RewardsCfg` dataclass — each field is a `RewardTermCfg` (`RewTerm(func=mdp.<reward_func>, weight=<float>, params=...)`). The composer is **sum**: total reward at step t is `Σ_i weight_i * func_i(env)`. Per-term decomposition is *free* — the manager already maintains a per-term running tensor accessible via `env.unwrapped.reward_manager._step_reward` (this is the hook `/add-reward-log` uses to populate `info["detailed_reward"]`). Sign convention: positive shaping terms (tracking-tanh, success bonuses), negative penalties (action-rate, joint-vel-l2, body-acceleration). Curriculum on weights is supported via `CurriculumCfg` + `mdp.modify_reward_weight` — Reach ramps `action_rate` from -0.0001 to -0.005 at `num_steps=4500`. Reward functions live in two places: shared utilities under `isaaclab.envs.mdp.rewards` (re-exported from `isaaclab.envs.mdp`), and per-domain extensions under `source/isaaclab_tasks/isaaclab_tasks/manager_based/<domain>/<task>/mdp/rewards.py` (Reach has its own `position_command_error`, `position_command_error_tanh`, `orientation_command_error`).

### File pointers

| What | Where |
|------|-------|
| Reward composition root | `source/isaaclab_tasks/isaaclab_tasks/manager_based/manipulation/reach/reach_env_cfg.py:RewardsCfg` (lines 134–161) |
| Per-term reward functions (task-specific) | `source/isaaclab_tasks/isaaclab_tasks/manager_based/manipulation/reach/mdp/rewards.py` (`position_command_error`, `position_command_error_tanh`, `orientation_command_error`) |
| Shared reward function library | `source/isaaclab/isaaclab/envs/mdp/rewards.py` (`action_rate_l2`, `joint_vel_l2`, `joint_pos_limits`, `flat_orientation_l2`, `track_lin_vel_xy_exp`, ...) |
| Composition operator | **sum** (RewardManager sums weighted terms; `composer="sum"` for `/add-reward-log`'s sanity assertion) |
| Curriculum on weights | `source/isaaclab_tasks/.../manipulation/reach/reach_env_cfg.py:CurriculumCfg` (`mdp.modify_reward_weight`); function in `source/isaaclab/isaaclab/envs/mdp/curriculums.py` |
| Reference task with rich reward | `source/isaaclab_tasks/isaaclab_tasks/manager_based/locomotion/velocity/velocity_env_cfg.py:RewardsCfg` (10+ terms — track-lin-vel, track-ang-vel, lin-vel-z penalty, ang-vel-xy penalty, joint-acc, action-rate, feet-air-time, undesired-contacts) |

> **Cross-link.** `/add-reward-log` already wraps every IsaacLab manager-based task automatically — `info["detailed_reward"]` is populated by reading `env.reward_manager._step_reward`. The `task_overview.md` Reward-logger column should read `yes` for any new manager-based task with no extra wiring required.

### Decisions the future agent must resolve

- Primary reward term and weight. For pose-tracking tasks the canonical pair is `position_command_error_tanh` (positive, weight≈0.1) + `position_command_error` (negative L2, weight≈-0.2). For locomotion: `track_lin_vel_xy_exp` (positive, weight≈1.0). For manipulation lift: `mdp.object_ee_distance` + `mdp.object_height` + sparse `mdp.object_lifted`. Ask user.
- Regularizers. `action_rate_l2`, `joint_vel_l2`, `joint_acc_l2` are the safe defaults. Weights typically -1e-4 to -1e-3. Ask only if the user has a task-specific stability concern.
- Sparse vs shaped. Default to dense shaping for early debugging — sparse-only training takes 10×+ samples. If the user explicitly asks for sparse, drop the `_tanh` term and add a single positive `mdp.is_at_goal`-style indicator with weight≈10.
- Curriculum. Add `CurriculumCfg` only if the user wants late-stage regularization ramping (Reach ramps action_rate from -0.0001 to -0.005). Skip for short trainings (<2k steps).

## §7 — Domain randomization (read by `dr-generator`)

### Description

DR is just more `EventCfg` terms — same dataclass that holds the §3 reset terms. The mode field selects when each term fires: `mode="startup"` runs once after the scene is built (use for material / mass / com randomization that should be fixed for the lifetime of the env); `mode="reset"` runs on every episode reset (use for per-episode action / observation noise resampling); `mode="interval"` runs every `interval_range_s` sim seconds during the episode (use for pushes, force-torque perturbations, command-resampling style DR). DR functions all live in `isaaclab.envs.mdp.events` and are named with a `randomize_*` prefix. Common axes: `randomize_rigid_body_material` (friction + restitution), `randomize_rigid_body_mass`, `randomize_rigid_body_com`, `apply_external_force_torque`, `push_by_setting_velocity` (velocity-perturbation push). The Reach task itself does not use DR — for a real DR example, see `source/isaaclab_tasks/.../locomotion/velocity/velocity_env_cfg.py:EventCfg` (`physics_material`, `add_base_mass`, `base_com`, `push_robot`).

### File pointers

| DR axis | Term / function | Path |
|---------|-----------------|------|
| Body mass | `mdp.randomize_rigid_body_mass` (operation ∈ {`add`, `scale`, `abs`}) | `source/isaaclab/isaaclab/envs/mdp/events.py`; example `source/isaaclab_tasks/.../locomotion/velocity/velocity_env_cfg.py:EventCfg.add_base_mass` |
| Body com offset | `mdp.randomize_rigid_body_com` | example `velocity_env_cfg.py:EventCfg.base_com` |
| Friction / restitution | `mdp.randomize_rigid_body_material` | example `velocity_env_cfg.py:EventCfg.physics_material` |
| Joint stiffness / damping | `mdp.randomize_actuator_gains` | `source/isaaclab/isaaclab/envs/mdp/events.py` |
| Observation noise | per-`ObsTerm.noise=Unoise(...)` (covered in §5 — not an EventCfg axis) | `source/isaaclab/isaaclab/utils/noise/noise_cfg.py` |
| Action noise | per-`ActionTerm` `noise` is **not** built in for IsaacLab manager-based — wrap policy actions externally if needed | `n/a` for the family |
| External pushes / force-torque | `mdp.apply_external_force_torque`, `mdp.push_by_setting_velocity` | example `velocity_env_cfg.py:EventCfg.push_robot` |
| Sensor / lighting (visual DR) | `mdp.randomize_visual_color`, `mdp.randomize_dome_light_color`, `mdp.randomize_visual_texture_material` | `source/isaaclab/isaaclab/envs/mdp/events.py` |

## Authoring conventions for downstream agents

- **Mirror, don't invent.** The canonical example file (`reach_env_cfg.py` + `config/franka/joint_pos_env_cfg.py`) is the source of truth. If a pattern is not in this doc but you find it in the example file, prefer the example.
- **Resolve ambiguity by asking the user once.** The "Decisions" sub-blocks list the questions that need user input. Batch them into a single `AskUserQuestion` per section, not one question at a time.
- **Per-section smoke is fatal.** A section is not "done" until its smoke check passes. Do not move to the next section on a smoke failure — diagnose, patch, retry, or escalate.
- **Stay surgical.** Adding a new task should add files under one new directory (`source/isaaclab_tasks/isaaclab_tasks/manager_based/<domain>/<task>/`) and one registration line per per-robot variant. Do not refactor sibling tasks.
- **Preserve the family idiom.** Manager-based tasks should not gain a `_reset_idx` body or a hand-rolled `_get_rewards`; that turns them into Direct-style envs and breaks the `RewardManager._step_reward` hook that `/add-reward-log` depends on.
